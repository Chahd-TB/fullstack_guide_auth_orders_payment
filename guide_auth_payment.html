2. 🔐 Authentication + JWT

Authentication = “Who are you?”

When a user logs in, the backend checks their email/password. If correct, it gives the frontend a JWT token.

Frontend
   ↓ email + password
POST /auth/login
   ↓
Backend checks User
   ↓
JWT token
   ↓
Frontend stores token

Why JWT?

HTTP requests are independent. The server needs a way to recognize the user on later requests. The token carries signed information about the authenticated user.

const token = jwt.sign(
  { userId: user._id, role: user.role },
  process.env.JWT_SECRET,
  { expiresIn: "7d" }
);

Notice the important field from our project: userId.

Sending the token

Authorization: Bearer <token>
Remember: Authentication is not the same as authorization. “Who are you?” = authentication. “What are you allowed to do?” = authorization.
🎯 Try it

Why would POST /orders need a JWT token?

Show answer
Because the backend needs to know which authenticated user is creating the order, so it can associate the order with that user.

Our user role

{

  role: "admin"

On the frontend we used logic like:

But hiding a button in React is not security. The backend must also protect the route.

router.delete(
  "/:id",

);
⚠️ Important: A malicious user can manually call your API. Never rely only on frontend checks for permissions.
🎯 Mini challenge

A normal user changes the frontend code and makes an “Admin Dashboard” button appear. Should they automatically gain admin access?

Answer
No. The backend must check the user's role before allowing admin-only operations.

4. 🔗 MongoDB Relationships with ObjectId + ref

We learned that MongoDB documents can reference documents stored in another collection.

user: {
  type: mongoose.Schema.Types.ObjectId,
  ref: "User",
  required: true
}

This means: store the User document's ID here.

FieldReferencesWhy?
Order.userUserWho placed the order?
Order.products[].productProductWhich product was ordered?
Payment.orderOrderWhich order is being paid?
Payment.userUserWho made the payment?

Why use both order and user in Payment?

Because they answer two different questions:

  • order → Which purchase is this payment for?
  • user → Which person owns this payment?

Population

Order.findById(orderId)
  .populate("user")
  .populate("products.product");

populate() lets Mongoose replace referenced IDs with the related documents when retrieving data.

🎯 Imagine it

If an Order contains user: "64abc...", does that string contain the user's whole name and email?

Answer
No. It is the user's MongoDB ObjectId. The backend can use that ID to find the related User document.

5. 🛒 Shopping Cart

The cart is mainly a frontend state problem until checkout.

cart = [
  {
    _id: "product123",
    name: "Bag",
    price: 2500,
    quantity: 2
  }
]

The core operations

ActionWhat happens?
AddIf product is new → add it. If already there → increase quantity.
Increasequantity + 1
Decreasequantity - 1, usually not below 1.
RemoveFilter that product out of the array.
TotalSum price × quantity for every item.
const total = cart.reduce(
  (sum, item) => sum + item.price * item.quantity,
  0
);
🧠 Key idea: reduce() turns many values into one value. Here, many cart items become one total price.
🎯 Calculate it

Bag = 2500 × 2. Shoes = 4000 × 1. What is the cart total?

Answer
2500 × 2 + 4000 × 1 = 9000.

6. 📦 Orders + Checkout

The important conceptual change is that a cart is temporary shopping state, while an order is a database record.

Cart→Checkout form→POST /orders→Order in MongoDB

Our Order structure

{
  user,
  products: [
    { product, quantity }
  ],
  totalPrice,
  customerInfo: {
    fullName,
    phone,
    wilaya,
    address
  },
  paymentMethod,
  paymentStatus,
  orderStatus
}
FieldMeaning
paymentStatusState of the payment: pending / paid / failed.
orderStatusState of the order: for example pending / confirmed.
customerInfoInformation needed to deliver the order.
Why separate paymentStatus and orderStatus?
An order can exist before payment succeeds. The payment state describes the transaction; the order state describes the order itself.
🎯 Scenario

An order was created but the card payment failed. Should the database pretend that the payment is “paid”?

Answer
No. The payment should remain failed/pending according to the flow, rather than falsely marking it paid.

9. 🖼️ Image Uploads + URLs

We encountered an important deployment bug: the frontend was still constructing image URLs using localhost.

Bad for production:

src={`http://localhost:3000${product.image}`}

Better:

const API_URL = import.meta.env.VITE_API_URL;

src={`${API_URL}${product.image}`}
Product.image→/uploads/image.jpg+API_URL→Full backend URL
Debugging lesson: When something works locally but breaks after deployment, inspect the actual URL the browser is requesting. “localhost” inside a deployed frontend is often a clue.

🎯 Debug challenge

Your deployed React app sends requests to http://localhost:3000. The backend is actually on Render. What is wrong?

Answer
The production frontend is using the local API URL. Set the production VITE_API_URL to the Render backend URL and redeploy.

11. 📱 Responsive Design

We learned to make the same UI adapt to different screen sizes instead of building a completely separate mobile application.

Tailwind's breakpoint idea

ClassMeaning
defaultMobile/base style
sm:Small screens and up
lg:Large screens and up
xl:Extra-large screens and up

Example:

text-2xl sm:text-4xl

Small screens use text-2xl; at the sm breakpoint and above, the title becomes text-4xl.

Our responsive pattern

<div className="flex flex-col lg:flex-row">

Mobile: stacked vertically. Large screens: side-by-side.

<div className="grid grid-cols-1 sm:grid-cols-2 lg:grid-cols-3">

Mobile: one column → small screens: two → large screens: three.

🧠 Rule: Start with the mobile layout, then add breakpoint changes for larger screens. Avoid trying to squeeze the desktop layout into a phone.

12. 🧩 How Everything Connects

Example: User buys a product

  1. User logs in → receives JWT.
  2. Frontend stores the authenticated user information/token.
  3. User adds products to the cart.
  4. User opens checkout.
  5. Frontend sends order information to POST /orders.
  6. Backend reads req.user.userId from the authenticated request.
  7. Backend creates an Order referencing the User and Products.
  8. Frontend creates a Payment for the order.
  9. Payment is processed using our test card simulation.
  10. Successful payment changes payment/order status.
Login→JWT→Cart→ Order→Payment→Confirmed

4️⃣ authController.js — Register + Login

Register

import bcrypt from "bcrypt";
import jwt from "jsonwebtoken";
import User from "../models/User.js";

export const register = async (req, res, next) => {
    try {
        const { name, email, password } = req.body;

        const existingUser = await User.findOne({ email });

        if (existingUser) {
            return res.status(400).json({
                message: "User already exists"
            });
        }

        const hashedPassword = await bcrypt.hash(password, 10);

        const user = await User.create({
            name,
            email,
            password: hashedPassword
        });

        res.status(201).json({
            message: "User registered successfully",
            user: {
                id: user._id,
                name: user.name,
                email: user.email,
                role: user.role
            }
        });
    } catch (error) {
        next(error);
    }
};

Login

export const login = async (req, res, next) => {
    try {
        const { email, password } = req.body;

        const user = await User.findOne({ email });

        if (!user) {
            return res.status(401).json({
                message: "Invalid email or password"
            });
        }

        const isMatch = await bcrypt.compare(
            password,
            user.password
        );

        if (!isMatch) {
            return res.status(401).json({
                message: "Invalid email or password"
            });
        }

        const token = jwt.sign(
            {
                userId: user._id,
                role: user.role
            },
            process.env.JWT_SECRET,
            { expiresIn: "7d" }
        );

        res.json({
            token,
            user: {
                id: user._id,
                name: user.name,
                email: user.email,
                role: user.role
            }
        });
    } catch (error) {
        next(error);
    }
};
🧠 Remember the chain: password → bcrypt hash → database
login → bcrypt compare → JWT → frontend

5️⃣ authMiddleware.js — Protect the request

import jwt from "jsonwebtoken";

const authMiddleware = (req, res, next) => {
    try {
        const authHeader = req.headers.authorization;

        if (!authHeader || !authHeader.startsWith("Bearer ")) {
            return res.status(401).json({
                message: "Authentication required"
            });
        }

        const token = authHeader.split(" ")[1];

        const decoded = jwt.verify(
            token,
            process.env.JWT_SECRET
        );

        req.user = decoded;

        next();
    } catch (error) {
        return res.status(401).json({
            message: "Invalid or expired token"
        });
    }
};

export default authMiddleware;

This is where our controller later gets:

req.user.userId
req.user.role
🧠 What does next() mean? It means: “I checked the request successfully. Continue to the next middleware/controller.”

🔟 paymentController.js — Create Payment

import crypto from "crypto";
import Payment from "../models/Payment.js";
import Order from "../models/Order.js";

export const createPayment = async (req, res, next) => {
    try {
        const { orderId } = req.body;

        const order = await Order.findById(orderId);

        if (!order) {
            return res.status(404).json({
                message: "Order not found"
            });
        }

        if (order.user.toString() !== req.user.userId) {
            return res.status(403).json({
                message: "Not allowed"
            });
        }

        if (order.paymentStatus === "paid") {
            return res.status(400).json({
                message: "Order already paid"
            });
        }

        const payment = await Payment.create({
            order: order._id,
            user: req.user.userId,
            amount: order.totalPrice,
            method: order.paymentMethod,
            status: "pending",
            transactionId: `TEST-${crypto.randomUUID()}`
        });

        res.status(201).json(payment);
    } catch (error) {
        next(error);
    }
};
Follow the logic:
Order ID → find Order → make sure it belongs to logged-in user → make sure it isn't already paid → create Payment.

1️⃣1️⃣ paymentController.js — Process the Test Payment

export const processPayment = async (req, res, next) => {
    try {
        const { paymentId, cardNumber } = req.body;

        const payment = await Payment.findById(paymentId);

        if (!payment) {
            return res.status(404).json({
                message: "Payment not found"
            });
        }

        if (payment.user.toString() !== req.user.userId) {
            return res.status(403).json({
                message: "Not allowed"
            });
        }

        if (payment.status === "paid") {
            return res.status(400).json({
                message: "Payment already processed"
            });
        }

        if (cardNumber !== "4242424242424242") {
            payment.status = "failed";
            await payment.save();

            return res.status(400).json({
                message: "Payment failed"
            });
        }

        payment.status = "paid";
        await payment.save();

        await Order.findByIdAndUpdate(
            payment.order,
            {
                paymentStatus: "paid",
                orderStatus: "confirmed"
            }
        );

        res.json({
            message: "Payment successful",
            payment
        });
    } catch (error) {
        next(error);
    }
};

🧪 Backend Trace Challenge

A logged-in user clicks “Pay”. The frontend calls processPayment(paymentId, cardNumber). Which function eventually checks whether the test card is correct?

Reveal
processPayment in paymentController.js. The route sends the request through authMiddleware first, then the controller runs.
🧪 Another one

Where does req.user.userId come from?

Reveal
The login controller puts userId into the JWT payload. Later, authMiddleware verifies the JWT and puts the decoded payload into req.user.
🧪 Final backend challenge

Why can't createOrder() simply trust a userId sent by the React frontend?

Reveal
Because client input can be changed. The backend should use the identity from the verified JWT, such as req.user.userId, instead of trusting a user ID supplied by the client.
